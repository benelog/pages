component-scan을 최소화하는 이유

component-scan@ConfigurationJSR-330MyBatis

2월 4일 글에서 component-scan과 @Component/@Service의 단점을 두 가지로 정리하고, @Configuration/@Bean으로 명시해 등록하거나 JSR-330 @Named를 쓰는 대안을 코드와 함께 제시했습니다. 어노테이션 붙은 클래스도 POJO라는 반론에는 "그것도 일리가 있는 말이다"라고 먼저 인정한 뒤 반박했습니다.

2월 16일에는 MyBatis가 RowMapper 같은 확장 지점을 왜 노출하지 않는지 물었습니다. 답을 정해 두지 않고 질문으로 남겼습니다.

  • 2021-02-04그래서 나는 스프링을 써도 component-scan을 최소화하거나 스프링 없이 손으로 DI하는 방식을 쓰곤한다.
  • 2021-02-16MyBatis 개발자는 RowMapper같은 인터페이스가 지나치게 Low level이라고 생각해서 노출하지 않은것일까?
  • 2021-04-16Java에 String interpolation은 아직 제안 조차 안 올라가 있다.
로깅

8월과 12월, 두 번 쓴 로깅 이야기

SLF4JLogbackLog4j

8월에는 slf4j-test 라이브러리를 소개하면서 SLF4J 1.x가 StaticLoggerBinder로 구현체를 찾는 방식의 문제를 길게 설명했습니다. 12월에 Log4j 취약점이 터지자 같은 주제로 돌아와, 개발자들이 SLF4J의 역할을 잘 모른다고 쓰고 KISA 안내문의 Logback 설명이 틀렸다고 짚었습니다.

  • 2021-08-17너무 오랫동안 로깅라이브러들은 아름답지 못한 방식으로 연결되어 있었다.
  • 2021-12-12'Java 로깅 프레임워크 생태계의 비극'이라는 제목으로 장문의 글을 쓰고 싶지만 언제할수 있을런지..
  • 2021-12-17개발자 중에서도 Logback이 Log4j 1.x에 의존관계가 있는것처럼 잘못 알고 있는 사람들이 있는 듯하다.
테스트

커버리지는 결과이지 목표가 아니다

4월 30일 동료의 컨퍼런스 발표를 보고 긴 의견을 남겼습니다. PowerMock처럼 static 메서드를 mocking하는 도구는 쓰지 말자는 쪽이고, 그 이유를 테스트 속도가 아니라 리팩토링 신호를 놓치게 된다는 데서 찾았습니다. 커버리지 수치를 조직 목표로 삼는 데 반대한 근거는 그런 조직에서 쓸모없는 테스트를 많이 봤다는 경험이었습니다.

  • 2021-04-30좋은 테스트를 만든 결과로서의 커버레이지가 높을수 있지만, 수치를 조직 전체의 목표로는 추구하고 싶진 않다.
  • 2021-04-30내가 쓰지 말자고 주장하는 이유는 테스트 성능보다는, 코드를 리팩토링할 신호를 무시할수 있게되기 때문이긴한다.

CONFIG.SYS에서 ON ERROR GOTO까지

GitHub 강의를 준비하다 DOS 시절 이야기로 빠진 1월 글을 시작으로 QuickBasic 자격증 사진, 하이텔 퇴마록, 1994년 잡지 광고가 이어집니다. 옛 기억은 대부분 지금 하는 일에서 출발합니다. 예외 처리를 고민하다 ON ERROR GOTO를 떠올리는 식입니다.

  • 2021-01-30DOS시절 게임하려고 EMS메모리니 XMS메모리니 하는 개념을 찾아보고 CONFIG.SYS, AUTOEXEC.BAT 같은거 만지작대던 기억이 떠오른다.
  • 2021-11-11비슷한 고민 몇년째 하고 있는지 생각해보다가 뜬금없이 ON ERROR GOTO 떠올라서 찾아봄.

정리

글 수는 줄었지만 한 편이 길어진 해. component-scan, MyBatis, SLF4J를 두고 "왜 이렇게 설계됐나"를 따진 글이 가장 길었고, 결정은 늘 나중에 바꾸는 비용으로 판단했습니다.

4월에 문·이과 선택 기사를 공유하며 쓴 문장이 이 관점을 그대로 보여 줍니다. "나중에 바꾸는 비용이 비싼 선택은 확신이 없을 경우 가급적 뒤로 미루면 장기적으로는 효율적이다."
